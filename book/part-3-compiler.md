# Part 3 — compiler

Part 3 builds a C compiler in Forth. Its layers, `cc/020` through
`cc/141`, are loaded by the seed after the library. They read C source
from standard input and write an executable or a relocatable object
directly, without a C compiler on the host emitting those bytes.

Start here after the library in Chapter 25. The loader selects compiler
layers after `forth/010-lib.fth`
(`forth-bootstrap/cc/compiler-layers.sh:2`); it does not load
`forth/130-asm.fth`.

At the first major comparison, the program being compiled is M2-Planet,
a C compiler that emits textual M1 assembly. Stage A compares that text
from two builds of M2-Planet; it does not assemble it. Chapter 38 explains
the comparison and what it establishes.

The Part has two halves. Chapters 27–38 build a compiler for the C subset
that M2-Planet is written in. The first half ends with the Stage A
comparison: Forth-built and GCC-built M2-Planet emit identical M1 when
compiling M2-Planet's own source. Chapters 39–49 extend the same compiler
toward GCC 4.0.4's source, adding the storage model, objects, calls and
language features that compiler needs.

- [Chapter 27](27-arena-and-io-buffers.md) sets up the arena and the I/O
  buffers that every later layer shares.
- [Chapters 28](28-the-preprocessor.md) and [29](29-the-lexer.md) turn
  source text into preprocessed tokens.
- [Chapter 30](30-types-and-symbols.md) records types and symbols.
- [Chapters 31](31-elf-and-codegen-part-1.md) and
  [32](32-codegen-part-2.md) emit ELF, instructions, calls and globals
  straight from Forth words.
- [Chapters 33](33-expressions-part-1.md)–[36](36-statements-if-while-for-return.md)
  parse expressions, declarations and statements.
- [Chapter 37](37-functions-and-scope.md) assembles whole translation
  units, and [Chapter 38](38-main-and-bootstrap-chain.md) adds the entry
  word and runs Stage A.
- [Chapters 39](39-lp64-storage-and-initializers.md)–[42](42-linker-and-archives.md)
  add LP64 storage, relocatable objects, System V calls, and a Forth
  linker with archives.
- [Chapters 43](43-runtime-and-libc.md) and [44](44-target-headers.md)
  supply the C runtime, libc and target headers.
- [Chapters 45](45-typed-constants.md)–[49](49-aggregate-abi.md) add typed
  constant expressions, varargs, floating values, bitfields and records
  passed by value.

The checkpoints exercise the layer just introduced: some inspect Forth
data or generated bytes; later ones compile and run small C programs.
Keep the selected target in view. The early core, native LP64 mode, and
System V object route have different storage and call contracts; loading
more source does not by itself select a target. Each checkpoint names its
selection and prerequisites. Consult the [C subset](60-c-subset.md) when
changing its C input.

Alongside those checkpoints, keep one short expression in view.
Chapter 28 expands `SQUARE(ROWS)`, with `ROWS` defined as 4, into the
tokens of `((4) * (4))`. Chapters 29–33 follow those characters as tokens,
typed operands and emitted instructions. That manual thread connects the
representations; it does not claim each intermediate layer can compile a
C program. The small layer-specific checkpoints isolate what is ready to
run at each stop.

By the end, you should be able to follow one expression from token to
instruction and one external call from an undefined symbol to a patched
address. Part 4 treats that machinery as a working compiler and asks a
new question: which tools can it build, and how can their ancestry be
checked?

## Reading the C input

Before Chapter 30, use this short bridge if C declarations are unfamiliar.
The goal is to distinguish values, addresses and type shapes so you can
explain what the compiler must remember. No prior C course or calling-convention
knowledge is needed. Experienced C readers can start with the predictions.

<details>
<summary>Read declarations, then predict what changes</summary>

This is a reading example, not an execution checkpoint. Imagine these
declarations inside a function:

```c
int n = 7;                      /* an integer object holding 7 */
int *p = &n;                    /* p holds n's address */
int **pp = &p;                  /* pp holds the pointer object's address */
int (*fp)(int);                 /* pointer to a function: int in, int out */
int a[3];                       /* three integer elements, not a pointer object */
struct point { int x; int y; };  /* a record type with named fields */
struct extent { int x; int y; }; /* another record type, despite matching fields */
struct point q;                 /* q is one point; q.x names its x field */
const int *view = &n;            /* pointer to an int accessed as const */
```

- **Address and value:** reading `p` gives the address of `n`; reading
  `*p` gives the integer stored there. In the declaration `int *p`, `*p`
  is the *declarator*: the name with its pointer shape. In the expression
  `*p`, the star follows the pointer, or *dereferences* it. Thus `*p = 9`
  changes `n`, not the address held in `p`.
- **Pointer depth:** `pp` holds `&p`; reading `*pp` gives the address
  stored in `p`, and reading `**pp` follows both steps to the integer in
  `n`. The types of `n`, `p` and `pp` are `int`, `int *` and `int **`:
  the same base kind with pointer depths zero, one and two. Chapter 30
  records that shape separately from the target's byte sizes.
- **Callable address:** the parentheses in `int (*fp)(int)` make `fp` a
  pointer to a function taking one `int` and returning an `int`. Unlike
  `p`, it would hold a function's address; this declaration alone gives
  it no valid address to call.
- **Shape and identity:** `a` has three elements, indexed `a[0]` through
  `a[2]`. A struct groups named fields; `point` and `extent` are *tags*
  naming distinct record types here. “Integer,” “pointer,” “array,” and
  “struct” therefore do not preserve the same information.
- **Qualification:** `const` restricts assignment through the qualified
  access. `*view = 9` is not allowed in ordinary C, but `view` itself can
  hold another address; `n` remains writable through `p`. Similarly,
  `const int a[3]` would qualify the array's elements.

**Predict before opening the feedback.**

1. After `*p = 9`, what do reads of `n`, `*view`, `**pp` and `p` give?
2. If `a[3]` becomes `a[4]` in its declaration, what must the compiler
   remember differently? Can one “struct” code distinguish `point` from
   `extent`?
3. Which assignment is allowed in ordinary C: `view = p` or `*view = 10`?
   Explain which part of `const int *view` is qualified.
4. Which pointer, `p` or `fp`, has a type describing a callable function?

<details>
<summary>Check the predictions and choose a repair</summary>

1. `n`, `*view` and `**pp` read as 9; `p` still holds `&n`, and `pp`
   still holds `&p`. A pointer is not a snapshot of the pointed-to value.
2. The element count changes from three to four. The element type stays
   `int`. The two struct tags need separate identities even though their
   fields match; one generic “struct” code loses that distinction.
3. `view = p` is allowed. `*view = 10` is not: the pointed-to `int` is
   qualified, not the pointer object `view`.
4. `fp`: the final `(int)` describes its function's parameter, not an
   integer object in memory. Compare its whole declaration with `int *p`.

If addresses or qualification tripped you up, draw one box for `n` and
two arrows, `p` and `view`, to it; mark the `view` route read-only. Retry
with `n` initially 5 and `*p = 8`: predict reads of `n`, `*view` and `p`
before checking them against your box and arrows. For shape or identity,
underline `[3]`, `point` and `extent`
in the declarations and explain which fact each adds. Keep this card
open in Chapter 30 if useful.

</details>

Chapter 30 maps these distinctions to type words and separate metadata.
Byte sizes depend on the selected target; the core parser also skips
qualifiers, while later paths retain qualifier information. The
[declaration chapter](35-declarations-types-globals.md#expectation-helpers-and-ignored-specifiers)
and [target contract](60-c-subset.md) establish those implementation limits.
The ordinary C meanings above follow [the C committee draft](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf),
sections 6.5.3.2, 6.7.2.3, 6.7.3 and 6.7.6. You don't need to read them,
and this compiler does not implement all of them.
